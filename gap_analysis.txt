1.1

🔴 CUSTOM Billing Cycle — Not in Flutter enum, UI, or Model

Backend BillingCycle enum
MONTHLY, QUARTERLY, YEARLY, CUSTOM

Flutter BillingCycle enum
monthly, quarterly, yearly

Warning:
The backend supports a CUSTOM billing cycle with customIntervalDays. The Flutter BillingCycle
enum has no custom value, SubscriptionRequest has no customIntervalDays field, and the UI
has no option for it. Furthermore, the Flutter Subscription response model completely lacks
a customIntervalDays field. If a user somehow has a CUSTOM subscription created via the
backend (e.g., every 15 days), the app's fromString() will silently default the enum to monthly
and completely lose the 15-day interval data because there is no field to store it from the
JSON.

1.2

🟢 User timeZone — Backend-only concern, no app work needed

Backend User entity
timeZone (String, default "UTC")

Flutter User model
Not mapped (intentionally)

Note:
The timeZone field exists so the backend's NotificationService can deliver due-date reminders
at a consistent local time (e.g., always 8 PM from the user's perspective), regardless of which
country they're in. This is entirely a backend responsibility — the server can infer the timezone
from device locale or registration metadata. No app-side settings or UI are needed for this.

1.3

🟢 User createdAt — Backend-only concern, same as timeZone

Backend User entity
createdAt (LocalDateTime)
Note:

Flutter User model
Not mapped (intentionally)

Similar to timeZone, this is a server-side record-keeping field. The backend tracks when users
registered for its own internal purposes (e.g., analytics, account management). There is no
current need to surface this in the app UI.

Note:
The backend already has the notification engine ready (currently logging "EMAIL SIMULATION"
placeholders). The app has preference toggles for notifications. The actual push notification
integration (e.g., Firebase Cloud Messaging, device token registration) is planned for a future
milestone. Once added, the backend's existing scheduling logic will deliver reminders at the
correct local time using the timeZone field.

🔴 householdId / Household object — Not in Flutter User model

Backend User entity
household (ManyToOne relation)

Flutter User model
No householdId or household field

❌

Caution:
While the backend correctly associates a user with a Household (via household_id), the Flutter
user_model.dart only maps id, email, fullName, and phoneNumber. For the app's "Household"
tab to function (e.g., fetching members, checking if the user is the admin, or querying
findByHouseholdId), the Flutter app must know the user's householdId. This needs to be added
to the Dart model and included in the backend's User DTO responses. Currently the app only
has instantial data but no logic, to be added later. Need to add a text based householdid thing
just so user can see it(non editable, auto generated)
